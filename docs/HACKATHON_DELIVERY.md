# ClaimPilot hackathon delivery guide

## 10-minute demonstration script

### 0:00–1:00 — Problem and product

- Introduce ClaimPilot as a consumer-support investigation workspace.
- Explain the problem: order messages, transaction records, policies, and
  receipts are fragmented.
- Point out the dashboard's seeded-demo label. Clarify that external accounts
  are not connected.

### 1:00–2:00 — Sign-in and dashboard

- Sign in with the configured local demo account.
- Show the authenticated dashboard and actual saved claim counts.
- Explain that protected API requests use a Flask session.

### 2:00–4:00 — Delayed-order investigation

- Select **Investigate delayed order**.
- Explain the real local MCP protocol work visible in the trace: sessions are
  initialized, tools are discovered, and discovered tools are invoked.
- Show Ledger transactions and duplicate checks, Inbox order matching, and the
  illustrative Policy result.
- Emphasize that the order and ledger data are seeded and Policy MCP content is
  not official merchant policy.

### 4:00–5:30 — Evidence Intelligence

- Open the matching claim's evidence list and analyze its PDF.
- Show the extracted invoice fields and comparisons with the claim.
- Explain that selectable PDF text is supported; scanned PDFs need OCR, which
  is not included.
- Save the analysis report, then use the saved-report control to demonstrate
  persistence.

### 5:30–7:00 — Human review

- Show the editable complaint template and the invoice details included after
  analysis.
- State clearly that the template is not generated by an AI model.
- Demonstrate **Reject draft** on a separate pending demo claim or approve the
  current draft. Approval records a demo action only; no email is sent.
- Attempting a second decision returns a conflict rather than executing again.

### 7:00–8:30 — Remaining MCP roles

- Run **Check transactions** and inspect possible duplicate groups in Ledger.
- Create a follow-up reminder through Calendar MCP.
- Add a clearly labeled demo warranty through Vault MCP.
- Point out that accepted Calendar/Vault results are persisted in local SQLite.

### 8:30–9:30 — Audit and persistence

- Reopen the claim and inspect its history: investigation start, server
  contact, discovery, invocation, result, evidence analysis, and user decision.
- Refresh the page and show that the claim, evidence report, and decisions
  remain available.

### 9:30–10:00 — Honest close

- Summarize the value: one reviewable investigation trail before a consumer
  acts.
- Repeat the key limitations: seeded data, illustrative policies, no AI
  service, no external email/refund, and no OCR.

## Presentation outline

1. **The problem** — Consumers must reconcile order, payment, policy, and
   purchase evidence across disconnected places.
2. **ClaimPilot** — An authenticated workspace for investigating and reviewing
   consumer issues before action.
3. **Architecture** — React/Vite, Flask sessions/API, SQLite, PyMuPDF, and an
   MCP client that discovers and invokes five stdio servers.
4. **Five MCP roles** — Inbox (order correspondence and demo approval), Ledger
   (transactions/duplicates), Policy (illustrative guidance), Calendar
   (validated reminder), and Vault (validated warranty).
5. **Evidence and human approval** — Invoice extraction/comparison, persistent
   PDF report, editable local draft, explicit approve/reject, and per-claim
   audit history.
6. **Demo truth and next steps** — Identify seeded/demo-only providers, lack of
   AI and OCR, and the integrations that would need real providers and
   authorization.

## Video pitch script (about 75 seconds)

> A delayed order can turn into hours of searching through emails, payments,
> policies, and receipts. ClaimPilot brings that investigation into one
> reviewable workspace. Its Flask backend uses real MCP sessions to discover
> and invoke five focused tools: Inbox, Ledger, Policy, Calendar, and Vault.
> Ledger can surface possible duplicate charges; Evidence Intelligence extracts
> selectable PDF text, compares invoice details with a claim, and saves a
> downloadable report. ClaimPilot prepares an editable complaint template, but
> the user decides whether to approve or reject it. Every recorded tool step
> and decision can be revisited in the claim history. This is an MVP: the
> connected data is seeded, policy text is illustrative, and approvals do not
> send email or move money. ClaimPilot demonstrates how MCP can coordinate a
> transparent investigation while keeping the consumer in control.
